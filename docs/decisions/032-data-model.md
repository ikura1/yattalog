# 032. データモデルの基本方針

- 日付：2026-10-10
- 状態：決定

## 背景
ステップ4として、ここまでの決定（特に 004、008、013、015、023、026〜029）と仕様レビュー（E5・E6・E12・S3・S4）を、データモデルに落とし込んだ。詳細は `docs/data-model.md` にある。

## 決定
- 主キーは UUID（v7）にする。記録の ID は端末で作る
- イベント・カテゴリ・記録・写真の持ち主は「スペース」にする。v1 では、ユーザーごとに個人用のスペースを1つ作る
- 記録は `local_date` を必ず持つ。時刻ありの記録は `occurred_at` と `timezone` も持つ
- Event に、最終記録日・記録回数・連続記録（連続回数と、連続の最後の期間の番号）をキャッシュする
- 並び順は文字列のソートキー（分数インデックス）で持つ
- 実績の定義はコードに持ち、DB には解除の記録だけを残す（ユーザー単位）
- R2 上のファイルの削除は、待ち行列のテーブル（StorageDeletion）を通して確実に行う
- Google のユーザーは `sub` で識別する

## 理由
- 連続記録のキャッシュに「連続の最後の期間の番号」を持たせると、日付が変わっても再計算せずに「連続中」「今の期間はまだ」「途切れた」を判定できる
- スペースを最初から挟んでおけば、共有に対応するときにデータ移行が要らない
- ファイル削除を待ち行列にすると、DB の削除と R2 の削除がずれても、後から確実に消せる（退会時の完全削除、決定 021）

## 影響・トレードオフ
- キャッシュと実データがずれないよう、記録の追加・編集・削除は必ずサービス層を通し、同じトランザクションの中でキャッシュを更新する。ずれを検出して直す管理用コマンドも用意する
- Log に space を複製して持つ（正規化はゆるめる）
