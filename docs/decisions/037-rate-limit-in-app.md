# 037. レート制限はアプリの中で、インスタンスごとに数える

- 日付：2026-10-11
- 状態：決定（レビュー S7）

## 背景
本番の URL は誰でもアクセスできる。β で知人に広げる前に、短時間に大量のリクエストを送られても、データが荒らされたり費用がふくらんだりしないようにしたい。

## 決定
- アプリ（Django のミドルウェア）で回数を数え、上限を超えたら **429** を返す。`Retry-After` で待つ秒数を伝える
- 1分あたりの上限（`settings.RATE_LIMITS`）
  - 記録の追加：60回（人ごと）
  - 書き込み全般：120回（人ごと。記録を含む）
  - ログインの入口と戻り先（`/accounts/`）：20回（接続元ごと）
  - すべてのリクエスト：300回（ログインしていれば人ごと、していなければ接続元ごと。静的ファイルは数えない）
- 数え方は固定の時間枠（1分ごとに 0 に戻る）
- 回数は**プロセス内のキャッシュ**に持つ。Cloud Run のインスタンスごとに別々に数える
- 接続元の IP アドレスは、`X-Forwarded-For` の**末尾**の値を使う（先頭は送る側が自由に書けるため）
- 外部のライブラリは使わず、自前で書く（`apps/core/ratelimit.py`）

## 理由
- **費用をかけない**ため。Google Cloud Armor は、ロードバランサー（月 $18 ほど）が前提になる。Redis などの共有キャッシュも有料。試験運用（α・β）の規模には見合わない
- DB（Neon）に回数を持つ案は、リクエストのたびに書き込みが増え、Neon の休止も妨げる
- インスタンスは最大2台なので、インスタンスごとに数えても、実際の上限は最大で2倍にしかならない。荒らしを止める目的には足りる
- 必要な処理は小さい（数十行）。依存を増やさないほうが、乗っ取りなどのリスクを減らせる

## 影響・トレードオフ
- 上限は厳密ではない。インスタンスが2台のときは最大2倍まで通り、インスタンスが入れ替わると回数は 0 に戻る
- 固定の時間枠なので、枠の変わり目をまたぐと、短い間に上限の2倍まで通ることがある
- 同じ接続元（会社や家の Wi-Fi など）から複数の人がログインしようとすると、接続元ごとの上限を分け合う。20回／分なので、ふつうの使い方では当たらない
- 上限を超えたリクエストも Cloud Run までは届く。インスタンスの上限（2台）が、費用の上限になる
- 一般公開で規模が大きくなったら、共有キャッシュか Cloud Armor に移す。上限の値とキーの作り方はそのまま使える
- API（v1）と書き出し（β）を作るときに、それぞれの上限を足す
