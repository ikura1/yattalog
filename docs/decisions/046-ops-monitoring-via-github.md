# 046. 監視は GitHub Actions と Cloud Logging で行い、Claude は GitHub 経由で確かめて直す

- 日付：2026-10-12
- 状態：決定

## 背景
α は本番（Cloud Run ＋ Neon、決定 033）で動いている。いまあるのは、予算アラート（月 ¥500）と、デプロイが失敗したときの GitHub の通知だけで、次のことに気づけない。
- 本番が落ちている
- 画面の裏でエラー（500）が起きている
- 遅くなっている、レート制限（決定 037）に当たっている

あわせて、「指示すれば Claude が本番を確かめて、直す」ようにしたい。制約は次のとおり。
- Claude の作業環境には Google Cloud の認証情報がない。Secret Manager などへの書き込みも権限で止められている
- **リポジトリは公開**。Issue も Actions のログ・サマリーも誰でも読める
- 費用はほぼ0円のまま。Neon の無料プランは計算時間に上限があり、5分ごとに DB を起こすと使い切る
- 標準エラーに出したログは、Cloud Run ではすべて重要度 ERROR になる（いまの Django のログがそう）。本物のエラーと見分けられない

## 決定
### 1. 気づく（自動）
| 何を | どうやって | 届き方 |
|---|---|---|
| 落ちていないか | GitHub Actions（`uptime.yml`）が1時間ごとに `/health` を叩く。`/health` は DB に触れない | 失敗したら Issue（ラベル `ops`）を開く。落ちている間は1時間ごとにコメントが増える |
| エラー | ログを1行1件の JSON にし（`apps/core/logging.py`）、例外を **Error Reporting** にまとめてもらう | 新しい種類のエラーは Error Reporting がメールで知らせる |
| 全体の様子 | GitHub Actions（`ops-report.yml`）が毎朝 9:07 に Cloud Logging を読み、リクエスト数・状態ごとの数・429・応答時間・5xx の経路・エラーをまとめる | 実行のサマリー。新しいエラーは種類ごとに Issue（`ops`）。同じものが開いていれば回数をコメントする |
| 費用 | 予算アラート（決定 033 のまま）。Neon の使用量は月1回、画面で見る | メール |

### 2. Claude が確かめる（GitHub 経由）
- Claude には Google Cloud の権限を渡さない。Claude は **GitHub だけ**を使う
  - `ops-report.yml` を手動で実行し（期間を指定できる）、サマリーと Issue を読む
  - `Deploy` の実行結果を読む
- `ops-report.yml` は、読むだけのサービスアカウント `yattalog-ops`（`roles/logging.viewer`・`roles/run.viewer`）で、キーを使わずに認証する（Workload Identity 連携。main からの実行だけ）。秘密の値と DB には触れない

### 3. 直す（いつもの流れ）
1. Yuki さんがプロジェクトで頼む（「本番を見て」「#NN を直して」）
2. Claude が報告と Issue から場所を絞り、テストで再現してから直し、PR を出す（CLAUDE.md の進め方どおり）
3. CI が通ったら Yuki さんがマージする（ここは変えない）
4. Claude がデプロイの成功を確かめ、`ops-report.yml` を短い期間で流し直して、エラーが止まったことを確かめてから Issue を閉じる

頼み方は `docs/operations.md` にまとめる。

### 4. 公開リポジトリに出すものは伏せる（レビュー S11）
`apps/core/ops_report.py` を通したものだけを、サマリーと Issue に出す。
- 経路の ID・数字・クエリは伏せる（OAuth の認可コード #49 もクエリに入る）
- 知らない経路は丸ごと伏せる（管理画面の URL は秘密、決定 033）
- エラーの本文と例外のメッセージは捨て、例外の種類と自前のコードの位置（ファイル:行 関数）だけを残す
- Cloud Logging から取り出した生のデータは、ランナーのファイルにだけ書き、使い終わったら消す。画面（ログ）には出さない

詳しい中身（本文・リクエスト）は、Yuki さんが Error Reporting の画面で見る。

### 5. Claude の定期巡回は、いまは入れない
毎朝の報告と Issue で足りる。Issue が増えて見きれなくなったら、Claude のルーチン（定期実行）で「毎朝 `ops` の Issue を見て、直せるものは PR にする」を足す。

## 理由
- 公開リポジトリの GitHub Actions は無料。Cloud Logging の読み出し、Error Reporting、Cloud Run への1日24回のアクセスも無料枠に収まる。月額は増えない
- Cloud Monitoring の稼働時間チェックとアラートも候補だったが、通知の設定が増えるうえ、Issue に残らないので Claude から見えない。Issue にしておけば、Yuki さん（リポジトリの通知）と Claude の両方が同じものを見られる
- Claude に Google Cloud の権限を渡すと、鍵の管理が増え、漏れたときの影響も大きい。GitHub 経由なら、読むだけの権限を Actions の中だけで使える
- `/health` を DB に触れないようにしたのは、1時間ごとに Neon を起こさないため。DB の不調は、毎朝の報告のエラーとして見える

## 影響・トレードオフ
- 落ちていると気づくまで、最大で1時間ほどかかる
- `/health` は DB が落ちていても 200 を返す
- Claude が見られるのは伏せたものだけ。メッセージが手がかりになるエラーは、Yuki さんに Error Reporting の画面を見てもらう（利用者のデータは貼らない）
- エラーの Issue は「例外の種類＋最後に通った自前のコードの位置」でまとめる。コードを変えて行番号がずれると、同じエラーでも別の Issue になることがある
- 初回だけ Yuki さんの作業が要る（`docs/operations.md` の「初回の設定」）

## 追記（2026-10-13）：経路を /healthz から /health に変えた
本番に入れた直後、`/healthz` が Google の 404 ページを返し、アプリまで届いていないことが分かった。
Cloud Run（Google のフロントエンド）は、`z` で終わる経路の一部を自分で使っていて、アプリには渡さない。
経路を `/health` に変えた。手元と CI では再現しない（Cloud Run の手前でだけ起きる）ので、テストで「z で終わらない」ことを確かめている。
