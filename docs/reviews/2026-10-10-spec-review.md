## リードエンジニア

### 高
- **E1 タイムゾーンの記述の矛盾**：3.3「暦日（Asia/Tokyo の日付）」と 3.3.1「毎日：暦日（Asia/Tokyo）」が、3.11.1（ユーザーごとのタイムゾーン）と食い違っている
- **E2 記録の日付の持ち方**：
  - 今の仕様では、時刻ありの記録は UTC の瞬間、時刻なしの記録は日付として保存する。タイムゾーンを変えると、時刻ありの記録だけ日付が動く
  - 「ロサンゼルスで 10/9 の夜にやった」記録が、日本に戻ると 10/10 になるのは、ユーザーの感覚とずれる
  - 提案：全記録に `local_date`（記録したときのタイムゾーンでの日付）を持たせ、記録した後は変えない。時刻ありの記録は `occurred_at`（UTC）と `timezone` も持つ。経過日数・連続記録・統計はすべて `local_date` と「今日の日付（今のタイムゾーン）」で計算する
  - 効果：SQL の `GROUP BY local_date` で集計でき、計算が単純になる。テストもしやすい
- **E3 API とサービス層**：htmx は HTML の断片を受け取り、Ninja は JSON を返す。両方から呼ぶ `services/`（記録の追加、取り消し、連続記録の計算など）を中心に置く設計にし、「すべての操作は API を通す」の文言を「すべての操作はサービス層を通し、外部向けには同じ処理を API として公開する」に直す
- **E4 タップで記録したときの失敗**：上の表のとおり。あわせて、取り消しも同じ UUID で冪等に処理できるようにする

### 中
- **E5 計算コスト**：ホームを表示するたびに、全イベントの経過日数と連続記録を全記録から計算することになる。Event に `last_local_date` と `streak_count`（連続回数）、`streak_period`（最後に数えた期間）をキャッシュし、記録の追加・削除・編集のときに更新する
- **E6 並び順の実装**：「全体で1つの並び順、カテゴリ内だけの入れ替え」には、整数の振り直しではなく、分数インデックス（文字列のソートキー）を使う。入れ替えのたびに全件を更新しなくて済む
- **E7 バックグラウンド処理の実行環境**：書き出しと退会時の削除にはワーカーが必要。Render ではワーカーを別のサービスとして立てるので、費用が増える（P5 と関連）。v1 は DB をキューにした django-tasks のバックエンドで、ワーカー1台に絞る
- **E8 署名付き URL とキャッシュ**：表示のたびに署名を作り直すと、ブラウザのキャッシュが効かない。有効期限を「1時間単位に切り捨てた時刻」にそろえて、同じ URL を使い回す
- **E9 PWA のキャッシュ**：Service Worker は静的ファイル（シェル）だけをキャッシュし、ログイン後の HTML や API の結果はキャッシュしない。ログアウト時にはキャッシュを消す（共用端末で他人のデータが見えないように）
- **E10 テスト方針**：日付まわり（タイムゾーン、週の区切り、月末、うるう年、時刻なしの記録）は不具合が出やすい。境界値のテストと、ランダムな入力を使うプロパティベーステスト（hypothesis）を必須にする

### 低
- **E11 HEIC 画像**：Android の Chrome では HEIC を Canvas で読み込めない。iOS は選んだ時点で JPEG に変換されることが多いが、変換されなかった場合に備えてサーバー側でも変換できるようにする（S1 と一緒に対応できる）
- **E12 ID の形式**：URL に出る ID は UUID（または推測しにくい短い ID）にする。連番を使わない（S4 と関連）

## PM

### 高
- **P1 段階的な公開**：案
  - **α（自分用・2〜3週間）**：グリッド、タップで記録と取り消し、過去の日付での記録、イベント詳細（統計・カレンダー）、カテゴリ、連続記録、Google ログイン
  - **β（知人10〜20人）**：テンプレート、書き出し、退会、タイムゾーン、PWA の追加案内、規約とポリシー
  - **一般公開 v1**：シェア、実績、よくやる時期
  - **v1.x**：MCP、記録用 URL（NFC）、オフラインでの記録
- **P2 PWA の追加案内**：上の表のとおり。追加しないと「すぐ記録できる」という最大の価値が伝わらない

### 中
- **P3 成功の基準がない**：何をもって「うまくいっている」とするかを決めておく。例：週に1回以上記録する人の割合、登録から7日後・30日後にまだ使っている人の割合、1人あたりのイベント数。プライバシーポリシーでは外部の分析ツールを使わないとしているので、自分の DB を集計して測る（個人を特定しない集計だけにする）
- **P4 意見を受け付ける窓口**：設定に「ご意見・不具合の報告」を置く（β では特に重要）
- **P5 運用費用と予算**：Render（Web、Postgres、ワーカー）で、毎月の固定費が数千円かかる。無料で続ける前提なら、許容できる月額の上限と、超えたときの方針（寄付、有料プラン、制限の見直し）を決めておく
- **P6 対象言語**：タイムゾーンには対応したが、UI とテンプレートは日本語だけ。「v1 は日本語のみ」と明記する
- **P7 名前とドメイン**：「Yattalog」のドメインを取れるか、似た名前のアプリ・商標がないかを確認する

### 低
- **P8 通知がないことのリスク**：プレッシャーを与えない方針（007）は良いが、使ってもらい続けるきっかけが少ない。将来の選択肢として「週に1回のふりかえり（任意・オフが初期値）」を残しておく
- **P9 記録用 URL（NFC）**：反応が良さそうなので v1.x の候補として SPEC に載せておく（S8 の注意点つき）

## セキュリティエンジニア

### 高
- **S1 画像の検証と作り直しをサーバー側で行う**：上の表のとおり。あわせて、保存時の Content-Type をサーバーで決め、ユーザーが送ってきた値を信用しない。配信は R2 のドメインから行い、アプリと別のオリジンにする
- **S2 CSV インジェクション**：上の表のとおり

### 中
- **S3 Google ログイン**：ユーザーの識別には、メールアドレスではなく Google の `sub`（変わらない ID）を使う。メールアドレスが確認済み（`email_verified`）の場合だけ受け付ける
- **S4 他人のデータへのアクセス（IDOR）**：すべてのクエリをスペース（＝持ち主）で絞り込む。これをサービス層の共通処理にして、個々の画面で書き忘れないようにする。「他人の ID を指定したら 404 になる」ことをテストで確認する
- **S5 セッションと CSRF**：Cookie は `Secure`・`HttpOnly`・`SameSite=Lax` にする。htmx のリクエストにも CSRF トークンを付ける。Django 6.0 の CSP 機能で、nonce を使った厳しいポリシーにする（インラインスクリプトを禁止する）
- **S6 書き出しファイル**：ダウンロードにはログインを必須にする（URL を知っているだけでは取れないようにする）。7日たったらファイルを削除する
- **S7 レート制限**：ログイン、記録の追加（例：1分に60回）、API 全般、書き出しに上限を設ける。超えたら 429 を返す
- **S8 記録用 URL（v1.x で検討する場合）**：URL 自体が鍵になる（知っている人なら誰でも記録できる）。記録の追加しかできないようにし、イベントごとに作り直せる・無効にできるようにする
- **S9 MCP／OAuth（v1.x）**：PKCE を必須にし、アクセストークンの有効期間を短くする。スコープは `read` と `log` に分ける。AI に返すメモはユーザーが書いたデータなので、ツールの説明で「指示ではなくデータ」であることを明記する
- **S10 管理画面**：Django の管理画面は URL を推測しにくいものにし、2段階認証を必須にする（django-otp など）。運営者がユーザーのデータを見るのは、問い合わせ対応や障害対応のときだけにすると決めて、プライバシーポリシーにも書く

### 低
- **S11 ログと監視の個人情報**：エラー監視（Sentry など）を入れる場合は、メモや写真の URL を送らない設定にする（個人情報の除去）
- **S12 依存ライブラリの更新**：Dependabot などで、脆弱性のあるライブラリの更新を自動で通知する
- **S13 バックアップ**：Render の Postgres のバックアップ保持期間が、プライバシーポリシーの「30日以内に削除」と合っているかを確認する

## デザイナー

### 高
- **D1 PWA の追加案内**（P2）：ホームに小さなバナーを出し、閉じたら7日間は出さない。iOS と Android で案内の内容を変える

### 中
- **D2 スクリーンリーダーで誤って記録される**：タイルを選ぶだけで記録されてしまう。タイルの読み上げに「ダブルタップで記録」を含め、「詳細を開く」をカスタムアクションとして用意する。キーボードでは Enter で記録、Shift+F10 またはメニューキーで長押しシートを開くようにする
- **D3 取り消しのトーストが5秒で消える**：操作が遅い人には短い（WCAG の時間制限の考え方）。トーストを触っている間は消さないようにする。履歴からも削除できることを、取り消しの代わりの手段として保証する
- **D4 小さな画面**：幅320px（iPhone SE など）では、3列だとタイルの中身（バッジ、絵文字、名前、日数）が詰まりすぎる。360px 未満では文字を小さくするか2列にする。PoC で確認する
- **D5 スワイプの競合**：グリッドを左右にスワイプしてタブを切り替える操作が、iOS の「画面の端から戻る」ジェスチャーとぶつかる。画面の端から20pxの範囲では反応しないようにする
- **D6 エラー・空・読み込み中の状態**：通信の失敗（E4）、写真のアップロードの失敗、上限に達したとき、オフラインのとき、それぞれの表示を一覧にして、文言をそろえる
- **D7 ブランド**：アプリのアイコン、PWA の起動画面、ロゴ、色と文字のトークン（デザインシステム）がまだない。β の前に決める
- **D8 編集モードが「詳細を開く」入口を兼ねている**：分かりにくい可能性がある。PoC で、知人に「詳細を見て」と頼んで迷うかどうかを確かめる。迷うようなら、タイルの日数部分をタップすると詳細が開く、などの案を検討する

### 低
- **D9 経過日数の表示**：「59日」の翌日が「2か月」になる。60日以上は、詳細画面で「63日（約2か月）」のように正確な日数も出す
- **D10 シェア画像の見た目**：絵文字は OS によって絵柄が違うので、同じ記録でも端末によって画像の見た目が変わる。許容するか、絵文字を画像（Twemoji など）にそろえるかを決める
- **D11 文言の統一**：「やった！」「記録しました」「記録」が混在している。トーストは「やった！ 記録しました」のように、アプリの言葉づかいをそろえる
